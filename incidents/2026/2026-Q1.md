**What happened.** At the start of January 2026 the Illinois Department of Human Services disclosed that health-related personal information about benefit recipients had been uploaded to a publicly accessible state website and left there. Reporting describes the material as having been reachable for more than three years before anyone noticed. A separate, unrelated Minnesota Department of Human Services incident was disclosed in the same window, and some aggregate reporting combines the two into a figure near one million people — which is why the scale here is given as a range rather than a number.

**Entry.** No attacker and no exploit. A file containing recipients' personal and health-related information was placed on a web location that required no authentication, by a person who intended it to be internal. Anyone who found the URL could read it.

**Escalation.** None required. The exposure point was the data itself; nothing further had to be reached or unlocked.

**Blast radius.** Hundreds of thousands of individuals served by the department, with health-related information among the fields exposed. Illinois did not publish a confirmed count at disclosure and no abuse was tied to the exposure at that point, so both the scale and the impact remain partially open.

**Human factor.** Someone published to the wrong place, and then nothing in the process looked again. A three-year exposure is not a single mistake — it is a single mistake plus the absence of any recurring check that enumerates what a government web property is actually serving to the public.

**What would have stopped it.** DATA-03 (storage and web-reachable locations private by default, with legacy paths audited), CLOUD-01 (nothing is publicly reachable unless it was decided to be, and the public surface is enumerated on a schedule rather than once), DATA-09 (retention limits, so a three-year-old extract is not still sitting there to be found).

```yaml
  - https://thehackernews.com/2026/04/toxic-combinations-when-cross-app.html
  - https://treblle.com/blog/moltbook-breach-breakdown
```

**What happened.** Moltbook launched as an "agent-first, human-second" social network where autonomous AI agents post to each other, and grew fast enough to attract high-profile attention. Researchers disclosed on January 31, 2026 that its entire production database was readable and writable by anyone with a browser. The exposure covered 35,000 email addresses and 1.5 million agent API tokens across roughly 770,000 active agents.

**Entry.** Moltbook shipped its Supabase project URL and publishable ("anon") key inside the client JavaScript bundle — which is normal and safe only if Postgres row-level security is enabled. It was not. With no RLS policy on the tables, that publicly visible key granted full read and write authority over every row in the database, exactly as if the service-role key had been published.

**Escalation.** None required, and this is the whole finding. There was no second step: the key visible in the page source was already the key to the database. Worse, the data was layered — private messages between agents contained plaintext third-party credentials, including OpenAI API keys agents had shared with one another, stored in the same unencrypted table as the tokens needed to hijack the agent itself.

**Blast radius.** 1.5 million agent API tokens (each of which allows impersonation of that agent), about 35,000 owner email addresses, owner-to-agent relationship mappings, claim tokens and verification codes, and private agent-to-agent messages containing live third-party API keys. No malicious exploitation was confirmed before the researchers reported it; the fix was two SQL statements enabling row-level security.

**Human factor.** A product built and shipped at high speed treated a Supabase default as a security decision that had already been made. Row-level security is opt-in, the publishable key is designed to be public, and the combination is only safe when someone explicitly writes the policy — nobody did, and nobody ran the one test that would have caught it.

**What would have stopped it.** DATA-01 (row-level authorization enabled and default-deny on every client-reachable table — literally the missing control here), DATA-02 (a negative test proving an anonymous visitor cannot read another user's row, run before launch), CRED-02 (anything the browser can read is public, so the key in the bundle must be harmless on its own), AGENT-02 (agent credentials scoped to the task and never co-located with third-party keys in a readable table).

```yaml
  - https://nimblebrain.ai/blog/state-of-mcp-security-2026/
```

**What happened.** OpenClaw is a self-hosted AI assistant that runs on a user's own machine and can read messages, manage email, browse, and run terminal commands. CVE-2026-25253 (CVSS 8.8), reported by Mav Levin of depthfirst and fixed in version 2026.1.29 on January 30, 2026, was publicly described from February 3, 2026: visiting a crafted web page was enough to take over the local OpenClaw gateway and run code on the host.

**Entry.** The OpenClaw Control UI read the `gatewayUrl` parameter from its own query string without validating it and auto-connected on page load, sending the stored gateway token in the WebSocket connect payload. A malicious link or page therefore received the victim's gateway `authToken` directly. Because the WebSocket endpoint did not validate request origin, the same flaw supported cross-site WebSocket hijacking against an instance bound to localhost — the "only listening on 127.0.0.1" assumption did not hold.

**Escalation.** The gateway token was the whole kingdom. With it an attacker could bypass authentication, disable the safety confirmations that are supposed to gate an agent's actions, escape container isolation, and execute arbitrary code on the host machine — an agent designed to run shell commands, now taking its instructions from a stranger.

**Blast radius.** No confirmed mass exploitation was reported. The exposure surface was the story: scans in January 2026 counted more than 42,000 OpenClaw instances reachable on the public internet, over a thousand of them running unauthenticated MCP endpoints leaking API keys, Slack credentials, and chat histories. Reported counts differ between scans, hence medium confidence on the figure.

**Human factor.** A tool that launched in November 2025 and reached scale in weeks was installed by individuals on their own machines, outside any corporate inventory, and frequently exposed to the internet so it could be reached from a phone. Nobody decided to publish 42,000 agent gateways; 42,000 people each made a small convenience choice.

**What would have stopped it.** AGENT-05 (no MCP server or agent endpoint exposed without authentication), AGENT-04 (agent runtimes and extensions pinned, reviewed, and version-diffed rather than auto-updated and forgotten), AUTH-11 (every state-changing interface authenticates its caller, including non-HTTP ones such as WebSocket gateways, and validates origin), CLOUD-08 (admin-equivalent interfaces are not on the public internet).


**What happened.** ShinyHunters ran a voice-phishing campaign against corporate and university staff through late 2025 and into early 2026. Harvard and the University of Pennsylvania both acknowledged intrusions into their alumni and development systems in the autumn of 2025; on February 4, 2026, after both institutions declined to pay, ShinyHunters published the stolen data — about 1.1 GB and over one million records from Harvard's Alumni Affairs and Development office, and about 483 MB and roughly 1.2 million records from Penn's development systems, 2.2 million in total. The fintech lender Figure Technology Solutions disclosed a social-engineering breach of nearly 967,000 user accounts in the same window, and further victims including CarGurus and Panera were attributed to the same campaign across January and February 2026.

**Entry.** A phone call. The caller impersonated internal IT support, walked the target to a typosquatted page imitating the organization's single sign-on portal, captured the credentials typed into it, and then asked the target to approve the multi-factor push notification that the attacker's own login had just triggered. Development and alumni-relations staff were specifically targeted — people who hold broad access to donor records and are not the population most security training is written for.

**Escalation.** Once an identity-provider account was taken, the attackers enrolled their own device for persistent MFA (Okta FastPass enrolment on emulated Android devices was observed in campaign analysis), then enumerated the connected application estate in rapid bursts and pulled bulk data out of whatever the single sign-on session unlocked — file shares, chat history, and CRM-style development databases. Single sign-on did exactly what it is built to do, for the wrong person.

**Blast radius.** 2.2 million alumni and donor records across Harvard and Penn, including email addresses, phone numbers, home and business addresses, event attendance, donation histories and amounts, wealth classifications, top-donor lists, and internal fundraising strategy. Figure reported 967,200 accounts with names, dates of birth, email and postal addresses, and phone numbers. Both universities refused to pay and the data was published; reported dates for Figure's disclosure differ between sources (mid-February and early March 2026), hence medium confidence.

**Human factor.** The campaign never needed a vulnerability. It needed one helpful person per organization to believe a phone call, and an MFA implementation that could be satisfied by tapping "approve". Every technical control in these organizations was intact; the identity-verification step at the start of the chain was a human judgement made under social pressure.

**What would have stopped it.** HUMAN-01 (identity verification for any credential or MFA action that is independent of what the caller claims — a callback to a known number, not a caller-supplied one), AUTH-09 (MFA that cannot be satisfied by a tap: number matching or, better, hardware keys, which would have made the fake SSO page useless), HUMAN-05 (training that reflects current technique, specifically inbound voice impersonation of IT support), DATA-11 (bulk export of a donor or customer database is a privileged, logged, alerting action, not a normal session behaviour).

**What happened.** Through late 2025 and into February 2026, several independent internet-wide scans found Model Context Protocol servers — the components that give an AI agent its tools — published to the public internet with no authentication at all. Knostic's scan unearthed 1,862 exposed MCP servers, and when researchers manually verified 119 of them, every single one permitted unauthenticated access to its internal tool listing. Trend Micro's earlier count of 492 had risen to 1,467 by a later scan, and February 2026 data put the unauthenticated share at about 41% of a much larger and fast-growing population. No attacker was needed for any of this; researchers simply looked.

**Entry.** MCP servers were deployed the way early internal microservices were: bound to a public interface for convenience, with authentication treated as something to add later. Reaching one required nothing beyond knowing the address. The verified instances published their full tool listing on request — a machine-readable inventory of what that organization's agents can do.

**Escalation.** None required. The exposed servers included production systems whose tools carried write access to financial databases, social media accounts, and CRM platforms. An MCP tool is an action, not a document: an unauthenticated tool listing with write-capable entries is an unauthenticated ability to act. Exposed instances also leaked agent conversation histories and environment variables containing OpenAI API keys, database credentials, and internal service tokens.

**Blast radius.** No confirmed mass exploitation at the time of disclosure — this is the researcher-found category, which is why it is worth recording. The exposure itself is the finding: a scannable public inventory of what thousands of organizations' agents are wired into, with credentials sitting in the environment beside it.

**Human factor.** Every one of these was deployed by someone solving a real problem quickly, usually outside the asset inventory, often on a developer's own cloud account. MCP has no authentication requirement that forces the question at deploy time, so the default outcome is exposure and the secure outcome requires a deliberate act.

**What would have stopped it.** AGENT-05 (no MCP server or agent endpoint exposed without authentication — the single control this entire record is about), AUTH-11 (every state-changing interface authenticates its caller, including non-HTTP ones), AGENT-02 (agent credentials scoped to the task, never admin or service-role, so an exposed tool cannot do everything), CLOUD-01 and CLOUD-09 in combination (enumerate what is publicly reachable on a schedule, and find the assets nobody owns).

```yaml

date_occurred: unknown
date_disclosed: 2026-02-25

escalation: [escalation/none-required]

  - https://research.checkpoint.com/2026/rce-and-api-token-exfiltration-through-claude-code-project-files-cve-2025-59536/
  - https://thehackernews.com/2026/02/claude-code-flaws-allow-remote-code.html
```

**What happened.** On February 25, 2026 Check Point Research published a write-up by Aviv Donenfeld and Oded Vanunu covering three flaws in Anthropic's Claude Code, all reached through configuration files that live inside a repository. Cloning an untrusted repository and opening it in the agent was enough to execute the attacker's shell commands or send the developer's Anthropic API key to an attacker-controlled endpoint. Anthropic had assigned and published CVEs for two of them (CVE-2025-59536, CVSS 8.7, fixed in 1.0.111; CVE-2026-21852, CVSS 5.3, fixed in 2.0.65), and all three were patched before the joint disclosure — hence no confirmed exploitation and high confidence in the technical account.

**Entry.** The repository was the payload. A `.claude/settings.json` file in a cloned project defines Hooks, which are shell commands the agent runs on lifecycle events such as session start. A `.mcp.json` file, combined with the `enableAllProjectMcpServers` option set to true, caused project-defined MCP servers to launch at tool initialisation. And a malicious `ANTHROPIC_BASE_URL` value in project configuration redirected the agent's authenticated API traffic to an attacker's proxy — Claude Code issued those requests before showing the trust prompt, so the key left before the user was asked whether to trust the directory.

**Escalation.** None required, which is the point. The developer machine is the destination: it holds the source tree, the cloud credentials, the SSH keys, and the session tokens. Code execution in the agent's context on that machine is already the crown jewels, no lateral movement necessary.

**Blast radius.** No in-the-wild exploitation was reported and no victim count exists. The reachable consequences were arbitrary code execution on the developer's machine with no user interaction beyond opening the repository, exfiltration of live Anthropic API keys with the attacker's costs billed to the victim, and access to project files and cloud-stored data the agent could reach. Every fix shipped between September 2025 and January 2026, ahead of publication.

**Human factor.** The habit being exploited is ordinary and universal: clone a repository, open it in the agent, let the agent start work. Nobody reads `.claude/settings.json` before doing that, in the same way nobody reads `package.json` scripts before running `npm install`. The design assumption that project-level configuration is authored by the person running the tool stopped being true the moment agents began being pointed at other people's repositories.

**What would have stopped it.** AGENT-08 (repository-level agent configuration reviewed as executable code, because that is what it is), AGENT-04 (MCP servers and agent extensions pinned and reviewed rather than auto-enabled by a flag in a file you did not write), AGENT-10 (production secrets and API keys kept out of any context an untrusted project can redirect), CICD-07 (open untrusted repositories in a managed, disposable environment that holds no credentials worth stealing).

```yaml
  - https://www.wiz.io/blog/trivy-compromised-teampcp-supply-chain-attack
```

**What happened.** Trivy is Aqua Security's open-source vulnerability scanner, run inside an enormous number of CI/CD pipelines precisely because it is the thing that checks whether everything else is safe. On March 19, 2026 an actor identifying as TeamPCP pushed a malicious `v0.69.4` tag at 17:43 UTC, triggering a release, and force-pushed almost every existing version tag in `aquasecurity/trivy-action` and all seven in `aquasecurity/setup-trivy` to commits containing an infostealer. Aqua published a security advisory and the compromise was reported publicly on March 20. It was the second compromise in about five weeks.

**Entry.** Credentials. A first compromise in February 2026 — an actor exploiting a pull-request workflow flaw — was contained incompletely, and the credential rotation that followed was not atomic, so the attacker plausibly captured newly rotated secrets during the rotation window itself. TeamPCP returned with valid credentials carrying tag-write access, and separately compromised Docker Hub credentials, and signed its imposter commits by spoofing the identities of real contributors.

**Escalation.** The tag force-push is the escalation, and it is elegant: pipelines that had done the right thing and pinned `trivy-action@v0.x` found that the pinned reference now resolved to the attacker's commit. Trust in the version tag carried the payload. Aqua's users then became the target — the definition of a supply-chain cascade — and the malicious binary also reached GitHub Releases, Deb and RPM channels, GHCR, ECR Public, and Docker Hub.

**Blast radius.** Individual exposure windows were short (roughly 3 hours for the binary, 12 for `trivy-action`, 4 for `setup-trivy`, 10 for the later Docker Hub images between March 22 and 23) but the surface was every pipeline that ran a scan in those windows. The payload scraped memory from the `Runner.Worker` process via `/proc/<pid>/mem`, swept 50-plus filesystem paths for SSH keys, cloud credentials, Kubernetes tokens, Docker and Git configuration, GPG keys, Slack tokens and cryptocurrency wallets, encrypted the haul with AES-256-CBC under RSA-4096, and shipped it to a typosquatted domain, falling back to staging the data in attacker-created GitHub repositories using stolen tokens. The binary also established systemd persistence on developer machines. Tag counts differ slightly between the advisory (76 of 77) and press reporting (75 of 76); no total victim count was published.

**Human factor.** Aqua's own advisory names it: containment after the February incident was incomplete and rotation was not atomic. Rotating a credential is not the control — rotating it in a way the attacker cannot observe is the control. Downstream, every affected team had done what the guidance says: they pinned a version and they ran a security scanner. Neither habit was wrong; both were load-bearing on the assumption that a version tag is immutable.

**What would have stopped it.** CRED-09 (a rotation and revocation runbook that treats rotation as atomic and assumes the attacker is watching — the control whose absence caused the second compromise), CICD-04 (pin pipeline actions to a commit SHA rather than a mutable version tag, which defeats the force-push entirely), CICD-03 (build provenance and artifact signing, verified at consumption, so a release produced outside the normal path fails a check), DEPS-03 (a cooldown before adopting a newly published version — the exposure windows here were hours), CICD-08 (treat the build system as production and monitor it as such, including the release automation of your security tools).


**What happened.** In late March 2026 the medical device manufacturer Stryker was hit by a destructive wiper operation attributed to the Handala Hack Team, a pro-Iranian persona assessed by researchers as operated by Iran's Ministry of Intelligence and Security. Tens of thousands of employee devices were remotely wiped and a large volume of company data deleted. It was described at disclosure as the first confirmed destructive wiper operation against a US Fortune 500 company, and Stryker said the incident was confined to its internal Microsoft environment.

**Entry.** Stryker did not disclose the initial vector, so this record carries `entry/unknown`. Researchers assessed — without confirmation from the company — that identity compromise via phishing was likely, and that credentials associated with Microsoft infrastructure, possibly obtained through infostealer malware, may have been used. That is an assessment, not a finding, and is recorded here as such.

**Escalation.** This part is reported rather than inferred, and it is the lesson: the destruction was delivered through Stryker's own device-management tooling. An identity with administrative rights in the Microsoft Intune and directory environment can issue a remote wipe to every enrolled device as a single, legitimate, fully supported administrative action. The attacker did not need malware on tens of thousands of endpoints; the fleet-management console was the weapon.

**Blast radius.** Tens of thousands of employee devices wiped and a large trove of company data deleted, with enterprise applications and internal systems disrupted. Stryker referenced the incident in securities filings but published no specific financial figure, and no precise device count was released, so both remain undisclosed here rather than estimated.

**Human factor.** Fleet management concentrates enormous destructive power into a small number of administrative identities, and organizations protect those identities as IT accounts rather than as the most dangerous capability in the building. A remote wipe of an entire device estate is a one-click, irreversible, company-stopping action that in most environments requires one person, one session, and no second approval.

**What would have stopped it.** AUTH-07 (admin and device-management tooling behind separate authentication with full audit, not reachable from an ordinary corporate session), AUTH-01 (phishing-resistant MFA on every identity with administrative reach, which removes the assessed entry path), HUMAN-02 and CLOUD-03 together (fleet-wide destructive actions require a second person and an IAM role that cannot issue them unilaterally), DATA-08 (restore-tested backups not writable by production credentials, which turns a wiper from an existential event into an expensive week).

## Countermeasures and guidance

- **Aqua Security published GHSA-69fq-xp46-6x23** naming safe versions (Trivy binary v0.69.2 and v0.69.3, `trivy-action` v0.35.0, `setup-trivy` v0.2.6) and the precise compromise windows, and Microsoft, Docker, Wiz, CrowdStrike, Palo Alto Networks, AppOmni and Legit Security each published detection, investigation and rotation playbooks within days — an unusually fast, coordinated downstream response to a compromise of a security tool.
- **The Trivy case made tag pinning a live argument rather than a theoretical one.** Because the attacker force-pushed existing version tags, teams that had pinned to `@v0.x` were hit and teams that had pinned to a commit SHA were not. CICD-04 moved from best practice to the difference between affected and unaffected.
- **Anthropic assigned and published CVEs for its own agent tooling** (CVE-2025-59536, CVE-2026-21852) and shipped fixes in Claude Code 1.0.87, 1.0.111 and 2.0.65 before Check Point's February 25 write-up — establishing, early, that agent configuration flaws get CVEs and coordinated disclosure like any other product vulnerability.
- **OpenClaw patched CVE-2026-25253 in version 2026.1.29 within days**, and national and institutional CERTs including Belgium's Centre for Cybersecurity and the University of Toronto issued patch-immediately advisories — the first time an AI personal-assistant vulnerability was treated by national CERTs as ordinary critical infrastructure guidance.
- **Snyk's ToxicSkills audit of 3,984 agent skills** (13.4% carrying at least one critical issue) and Antiy CERT's count of 1,184 malicious skills gave the agent-skill ecosystem its first empirical baseline, and pushed marketplace review and publisher verification onto the agenda of every agent platform.
- **Repeated internet-wide MCP scans** by Knostic, Trend Micro and others turned "expose an MCP server without authentication" from an abstract risk into a measured population, and drove the zero-trust framing for agent tooling: authenticate the caller of a tool endpoint the same way you would authenticate the caller of an admin API.
- **Supabase row-level security became the quarter's most-repeated remediation.** The Moltbook exposure was fixed with two SQL statements, and the case was widely cited afterwards as the canonical example of why a publishable client key is only safe when default-deny RLS is enabled first — a default that has to be chosen, not inherited.
