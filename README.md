# Cyber Security Checklist

**A security checklist derived from how organizations were actually breached between 2016 and
2026 — installable as a Claude Code plugin, usable as a copy-paste prompt, readable as a
document.**

Most security checklists are written from first principles and read like a list of things a
careful person would probably do. This one is written backwards: from a corpus of documented
breaches, through the mechanism each one used, to the control that would have broken the chain.
Every item cites the incident that produced it.

That matters because the failures are not exotic. In 2025 a researcher scanned 1,645
applications generated by one AI app builder and found 170 serving their whole database to anyone
who asked (CVE-2025-48757) — the same kind of mistake, a door left open by default, that cost Uber
57 million records in 2016. Knowing *that* a control exists changes nothing. Knowing what it cost
the last six companies that skipped it changes behaviour.

## Install as a Claude Code plugin

```shell
/plugin marketplace add sogangCSmaster/cyber-security-checklist
/plugin install security-checklist@cyber-security-checklist
```

That gives you three skills and a hook:

### `secure-by-default` — applied while you write

Claude loads it when generating code that touches user data, credentials, authentication,
database access, uploads, dependencies, or agent tooling. It does not ask permission for
defaults; it writes the secure version and tells you in one line what it did.

> Enabled RLS with a default-deny policy on `profiles` in the same migration, and added a test
> asserting user A gets zero rows for user B. Supabase tables are readable by anyone with the
> anon key until a policy exists.

Whether a skill loads is the model's call, so the mechanical part does not depend on it: a
**write-time hook** checks every file Claude writes or edits, and reports only what that change
introduced — a committed secret, `service_role` in client code, SQL built from strings, a table
created without row-level security, an unsafe CI workflow. It needs `python3`; without it the hook
does nothing. Turn it off with `SECURITY_CHECKLIST_HOOK=off`.

### `/security-checklist:security-audit` — audits what already exists

Runs [a scanner](./skills/security-audit/scripts/scan.py) with about forty checks — secrets in
the tree and in git history, row-level security and Firebase rules, SQL, command and HTML
injection, mass assignment, lockfiles and install scripts, CI workflows, agent configuration,
IaC, CSP — then reads what a scanner cannot judge, such as per-object authorization, and makes
every finding carry the incident that proves it matters:

> **Supabase `profiles` table has no row-level security** — `DATA-01`
> `supabase/migrations/0002_profiles.sql:14`
> Any holder of the anon key — which is in the client bundle, so everyone — can read every row.
> *Precedent:* Lovable shipped generated apps without RLS; 170 of 1,645 scanned apps were exposed
> (`I2025Q2-12`, CVE-2025-48757). Moltbook repeated it in 2026 and exposed 1.5M API tokens
> (`I2026Q1-09`).

The scanner reports every check as ran, not run, or error, so a check that could not run is never
mistaken for a clean one. It skips dependencies and build output, masks every secret it prints,
and can limit itself to a path or to what a branch changed (`--diff origin/main`), marking each
finding as introduced or pre-existing. Pre-approved commands are only the scanner and read-only
git; a build or a request to a live host asks you first.

This skill was called `security-review` before version 0.2.0. The name changed because a
personal skill with that name replaces Claude Code's built-in `/security-review`.

### `/security-checklist:ship-gate` — the last checkpoint

Eight blocking gates and ten should-fix gates, ordered by how often each failure actually
appears in the corpus. Returns **SHIP** or **DO NOT SHIP**, with evidence for every gate. It scans
the built bundle, not just the source, and asks you once for what a repository cannot show — MFA,
backups, who gets alerted. A gate you vouched for is reported as attested, a gate nobody could
check as unverified, and an unverified blocking gate means do not ship.

### Without the plugin

Try it without installing anything:

```shell
git clone https://github.com/sogangCSmaster/cyber-security-checklist
claude --plugin-dir ./cyber-security-checklist
```

Or copy the skills into a skills directory:

```shell
cp -r cyber-security-checklist/skills/* ~/.claude/skills/     # all your projects
cp -r cyber-security-checklist/skills/* .claude/skills/       # just this one
```

Copied skills keep the scanner and the per-control precedents that ship inside
`security-audit/`, so the audit and the gate work. What they lose is the full incident corpus and
the checklist files the skills link to, and the hook, which only a plugin installs. To add the hook
yourself, put this in `~/.claude/settings.json`:

```json
{
  "hooks": {
    "PostToolUse": [{
      "matcher": "Write|Edit|MultiEdit",
      "hooks": [{ "type": "command", "command": "python3 ~/.claude/skills/security-audit/scripts/scan.py --hook", "timeout": 30 }]
    }]
  }
}
```

## The evidence

[`incidents/`](./incidents/) holds **861 records across all 43 quarters from 2016 Q1 to 2026 Q3**.
Each record separates three things that are usually blurred together, because they need three
different fixes:

| | Question | What it maps to |
| --- | --- | --- |
| **Entry** | How did they get the first foothold? | Prevention |
| **Escalation** | Why did one foothold become many? | Blast radius — segmentation, scoping, least privilege |
| **Reach** | How far did it finally go? | Detection, retention, data minimization |

Plus a **human factor** field on every record, because every incident has one — someone chose the
default, skipped the review, or deferred the patch.

Records carry a closed vocabulary of tags across seven namespaces, so one `grep` selects one
dimension:

```bash
grep -rl 'entry/secrets-in-repo' incidents/20*/       # every incident that began with a committed key
grep -rho 'factor/human-error' incidents/20*/ | wc -l # how often plain human error is the root cause
grep -rlE 'tech/(firebase|supabase)' incidents/20*/   # everything involving a client-queried backend
grep -rl 'DATA-01' incidents/20*/                     # which incidents does this control answer for?
```

[`incidents/PATTERNS.md`](./incidents/PATTERNS.md) is the rollup.
[`incidents/CONTROL-INDEX.md`](./incidents/CONTROL-INDEX.md) maps every control to the incidents
it would have broken — and marks those that are preventive (the newer hardening domains include
controls with no single disclosed incident behind them; the index says which).
[`incidents/INDEX.md`](./incidents/INDEX.md) is one line per incident.
[`incidents/STATS.md`](./incidents/STATS.md) is the frequency rollup that the checklist's ordering
comes from. [`incidents/index.jsonl`](./incidents/index.jsonl) is the machine-readable version, and
[`precedents.md`](./skills/security-audit/references/precedents.md) is the per-control citation list
the audit skill ships with. All of them are generated:

```bash
python3 tools/build_index.py           # rebuild
python3 tools/build_index.py --check   # validate, and fail if a generated file is out of date
```

### Three things the evidence says that most security advice does not

- **Half of all breaches involved no escalation at all.** `escalation/none-required` appears in
  **52%** of records — the bucket was public, the database had no password, the endpoint answered
  anyone who asked. There was no chain to break.
- **The most common published answer to "how did they get in" is silence.** `entry/unknown` is
  **39%**, many times the next vector. The distribution of published entry vectors is
  not the distribution of real ones.
- **The top three root causes are organizational.** Process failure (26%), detection failure (23%)
  and third-party trust (20%) all outrank every purely technical class. Zero-days are 3%.

Full working in [`incidents/PATTERNS.md`](./incidents/PATTERNS.md).

### What the corpus is and is not

It is **curated and representative**, not exhaustive. Thousands of breaches are disclosed
annually and most are never described in enough detail to learn from. Each quarter holds 8–14
records chosen to span the full range of failure modes rather than the largest headline numbers,
with ordinary human error and process failure deliberately over-represented — a misconfigured
bucket teaches more about prevention than a nation-state zero-day, and it is far more likely to
be your problem.

It is **skewed toward what gets reported**: consumer data and regulated industries dominate, and
`sector/tech` alone is 239 of 861 records. It is *less* skewed geographically than most breach
compilations — 404 of 861 records are from outside the United States and the United Kingdom,
across 81 distinct regions — because the second pass searched local outlets and regulators rather
than English-language aggregators. It is still not proportional to where breaches actually happen,
and [`incidents/PATTERNS.md`](./incidents/PATTERNS.md) says so.

## Contributing

Add an incident:

1. Read [`incidents/SCHEMA.md`](./incidents/SCHEMA.md) and follow the record format exactly.
2. Use only tags defined in [`incidents/TAGS.md`](./incidents/TAGS.md). To add a tag, define it
   there first.
3. File it in the quarter of its **disclosure**, not its intrusion, recording both dates.
4. Cite at least one source, preferring regulators, court filings, and the victim's own
   post-mortem over press coverage.
5. Run `python3 tools/build_index.py` and commit the regenerated index with your record.

The `confidence` field exists so a reader can tell a regulator's finding from an attacker's
boast. If a number was never disclosed, the record says `undisclosed` — it does not say a guess.

Change a check. The scanner's regression tests run against fixture apps in
[`tests/fixtures/`](./tests/fixtures/) — a vulnerable Next.js and Supabase app, a vulnerable Flask
app, and a clean app that must raise no false alarm — and pin both what each check must find and
what it must leave alone. Fixture files hold placeholders instead of real-shaped keys, so this
repository never trips secret scanning. CI runs the first two commands; run the third before you
push:

```bash
python3 tools/build_index.py --check
python3 -m unittest discover -s tests -v
claude plugin validate --strict .claude-plugin/plugin.json   # needs the Claude Code CLI
```

The skills themselves — whether they trigger, and what they report — are measured with
`claude plugin eval`; see [`evals/README.md`](./evals/README.md).

Add a control. The corpus-derived core controls each map to at least one incident that they would
have stopped — that is what keeps the list honest, and [`incidents/CONTROL-INDEX.md`](./incidents/CONTROL-INDEX.md)
shows it. The hardening domains added later (browser-trust headers, mobile, parts of crypto and
business-logic) also include **preventive** controls that no single disclosed incident proves; the
index marks each of those "no incident cites this yet" rather than inventing one. If you add a
control, either cite the incident it would have broken or say plainly that it is preventive.
